# 迭代五：引擎行动与战斗

> 目标：在迭代四骨架上实现行动阶段操作、战斗阶段攻击流程与胜负判定，使引擎可在无效果系统前提下跑通「调度 → 抽卡 → 行动 → 战斗 → 胜负」。
>
> 前置依赖：迭代四 `GameState` / `PlayerState` / `FieldZone` / `CardInstance` / `GameEngine` / `PhaseType` / `Zone` / `RuleConstants` 等已就绪。
>
> **强制约束**（详见详细设计 §1.3）：
> - `engine` 包仍为纯 POJO：禁止 Spring / MyBatis / `common` 依赖
> - 注释标注规则条款编号；非法操作抛 `EngineException`（含 `ruleRef`）
> - Handler 无状态；先 `validate` 再 `execute`；状态一律读写 `GameState`

### 与迭代四的命名约定（必读）

| 类 | 包 | 含义 |
| --- | --- | --- |
| `com.aris.mtcg.engine.phase.ActionPhaseHandler` | 迭代四 | 阶段处理器：进入 `PhaseType.ACTION` 时回调 |
| `com.aris.mtcg.engine.action.ActionTypeHandler` | 本迭代 | 操作处理器接口：处理一种 `ActionType` |

二者职责不同，类名已区分，实现时按包与接口分别引用即可。

### 与现有模型的 as-built 对齐

| 设计稿写法 | 现有实现 | 处理 |
| --- | --- | --- |
| `field.getBase().add(card)`（List） | `FieldZone.base` 为 `CardInstance[MAX_BASE]` | 找空槽写入；`isBaseFull()` 已有 |
| `card.getCardType()` / `getLevel()` | 在 `CardSnapshot` 上 | 经 `instance.getSnapshot()` 读取 |
| `state.appendActionLog(...)` | `GameState.logAction(ActionLog)` | 沿用现有 API；`ActionLog` 字段可按需扩展或适配 |
| 设计稿未单列 `CombatContext` | 战斗 Handler 依赖之 | **本迭代补建**并挂到 `GameState` |

## 步骤详解

### 步骤 1：操作框架

**目录**：`engine/action/`

1. `ActionType`：16 常量（含 `MULLIGAN` 登记，实现可委托已有 `GameInitializer.mulligan`）
2. `ActionRequest` / `ActionResult`（含 `success` / `phaseAdvanced` / `gameEnded` / `winnerId`）
3. `EngineException(message, ruleRef)`
4. `ActionTypeHandler`：`supportedType` / `validate` / `execute`
5. `ActionDispatcher`：`register` / `dispatch`（先 validate 再 execute）；可选 `handlerOf(type)`

**检验**：`mvnw.cmd compile`；包边界无 Spring/`common`。

---

### 步骤 2：CombatContext + GameState 挂接

战斗流程需要运行时上下文（设计 §4 / §7.1），详细设计文件清单未单列但代码引用了 `state.getCombatContext()`。

建议最小字段：

| 字段/方法 | 用途 |
| --- | --- |
| `CombatStep step` | ADJUST / TARGET / COMBAT_RESPONSE / RESOLUTION / … |
| `CombatRow row` | 当前攻击行（先锋→侧翼→后卫→FINISHED） |
| `CardInstance attacker` / 目标区或目标实例 | 锁定攻击 |
| 应对号召已用标记、连续 PASS 计数 | 303.2.a.4.3.2 |
| `advanceRow()` / `endCombat()` / `isBothPassedConsecutively()` | 协作 API |

`GameState` 增加可空 `combatContext`（非战斗阶段为 null；进入战斗时新建）。

**检验**：可 `new CombatContext()` 并挂到 `GameState`。

---

### 步骤 3：DistanceCalculator + WinChecker

**参照**：详细设计 §5、§6

| 类 | 要点 |
| --- | --- |
| `DistanceCalculator` | 战区线性路径距离；与矩阵一致；`canReach(attacker, zone)` |
| `WinChecker` | 103.1.a 时间线 ≥9；103.1.b 对方卡组空；`declareWin` 留给迭代六；写 `FINISHED` + `winnerId` |

注意：103.1.b「对方卡组=0」与迭代四 `DrawHandler.checkWinByDeck` 语义对齐或逐步统一到 `WinChecker`（推荐抽卡后也调 `WinChecker.check`）。

**检验**：单测距离矩阵若干格；时间线 9 / 空卡组结束对局。

---

### 步骤 4：行动 Handler — 部署 / 号召 / 移动

| Handler | 规则要点 |
| --- | --- |
| `BaseDeployHandler` | 阶段限 1；基地未满；角色卡盖入基地；抽 1；`enteredThisTurn` |
| `SummonHandler` | 限 3（先攻首回合 1）；Lv4+ 撤退合计 Lv（战区+基地，盖卡计 Lv1，Q&A Q7）；目标可为战区空位或基地（Q&A Q1）；同名唯一校验按设计 |
| `CombatBaseMoveHandler` | 每角色每回合 1 次；本回合进场不可移；战区↔基地 |

公共校验：`assertActivePlayer`、`assertPhase(ACTION)`。

**检验**：单测合法部署/超限失败/`EngineException.ruleRef`。

---

### 步骤 5：盖卡翻开 / 结附解除 / 启动骨架 / 结束 / 认输

| Handler | 要点 |
| --- | --- |
| `SetFaceDownHandler` / `FlipFaceUpHandler` | `faceDown`；翻开清 `enteredThisTurn`（按设计） |
| `AttachHandler` / `DetachHandler` | 结附不占号召次数（Q&A Q8）；不清除结附卡效果定义（Q&A Q3） |
| `ActivateEffectHandler` | validate 阶段/权限；execute 返回「未实现」或空成功骨架，**不**引入效果引擎 |
| `EndPhaseHandler` | 行动阶段 → 推进到 COMBAT；与 `GameEngine.endActionPhase` / `advancePhase` 对齐 |
| `SurrenderHandler` | 对手获胜，立即 `FINISHED` |

**检验**：结附后 `summonCount` 不变；认输后 `winnerId` 为对方。

---

### 步骤 6：战斗 Handler

| 组件 | 要点 |
| --- | --- |
| `CombatAdjustHandler` | 最多 4 次战区互换；不计移动 |
| `AttackSequenceHandler` | 锁定攻击者与目标；按行推进；与 `CombatContext` 协作 |
| `CombatResponseHandler` | PASS / RESPONSE_SUMMON / INTERCEPT；目标失效回 TARGET（Q&A Q9）；不可取消攻击 |
| `BattleResolver` | 战力比较；败者撤退；破绽 → 冲击顶进时间线；后调 `WinChecker` |

改造 `phase.CombatHandler`：先攻首回合仍跳过；非首回合进入战斗时初始化 `CombatContext`，**不要**再无条件直接 `advancePhase`（改为等 `END_PHASE` / 攻击序列结束再推进）。具体等待点以实现时与详细设计 §4 对齐为准。

**检验**：破绽攻击进时间线；战力相等双方撤退；拦截改目标。

### 步骤 7：GameEngine 装配

1. 构造时 `new ActionDispatcher()` 并 `register` 全部操作 Handler
2. 暴露 `dispatch(ActionRequest)` → `dispatcher.dispatch(state, request)`，成功后可按需 `WinChecker.check`
3. `END_PHASE` / `endActionPhase` 统一走 Dispatcher 或保持薄封装调用 `EndPhaseHandler`
4. `MULLIGAN`：Dispatcher 转调 `GameInitializer.mulligan` 或独立 Handler
5. 保证包边界与现有单测：`startGame` → ACTION 仍成立；结束后可 `dispatch` 部署等

**检验**：`GameEngineTest` 旧用例仍通过；新增「部署一次」集成用例。

## 实现注意（易错点）

1. **命名**：阶段用 `ActionPhaseHandler`，操作用 `ActionTypeHandler`，勿混用包与职责
2. **基地数组**：写入空槽，勿当 List.add
3. **号召撤退**：遍历整个 `FieldZone`（战区+基地），盖卡 Lv=1（Q&A Q7）
4. **应对号召目标**：允许 `Zone.BASE`（Q&A Q1）
5. **应对后目标失效**：回 `TARGET` 重选，不可取消攻击（Q&A Q9）
6. **结附**：不占号召次数；不清效果定义（Q&A Q8 / Q3）
7. **ActivateEffect**：本迭代禁止偷偷实现效果引擎
8. **胜负**：关键路径统一走 `WinChecker`，避免多处 rival 逻辑不一致
