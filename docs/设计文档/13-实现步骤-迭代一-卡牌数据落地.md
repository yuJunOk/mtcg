## 步骤 1：切换数据库 SQLite → PostgreSQL

### 实现内容

1. `pom.xml`：移除 `sqlite-jdbc` 依赖，添加 `postgresql` 驱动
2. `application.yml`：修改数据源连接为 PostgreSQL

### 设计意义

需求分析阶段已决策（Q5）：PostgreSQL 支持 JSONB（对局状态存储）、全文检索（卡牌搜索）、OLTP 事务（在线并发）。SQLite 不适合在线对战场景的并发写入。这一步是所有后续功能的基础——没有正确的数据库，后面的代码都是空中楼阁。

### 涉及文件

| 文件 | 操作 |
| --- | --- |
| `pom.xml` | 移除 sqlite-jdbc，添加 `org.postgresql:postgresql` |
| `application.yml` | 修改 datasource url/driver 为 PostgreSQL |

### 关键改动

**pom.xml**：
```xml
<!-- 移除 -->
<!-- <dependency>
    <groupId>org.xerial</groupId>
    <artifactId>sqlite-jdbc</artifactId>
</dependency> -->

<!-- 添加 -->
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
</dependency>
```

**application.yml**：
```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/mtcg
    driver-class-name: org.postgresql.Driver
    username: postgres
    password: your_password
```

### 检验效果

- 项目能正常编译（`mvn compile`）
- 启动应用，日志中看到 PostgreSQL 连接成功（无报错）
- 如果连接失败，检查 PostgreSQL 服务是否启动、数据库 `mtcg` 是否已创建

## 步骤 2：重建卡牌表结构

### 实现内容

重写 `init.sql`，按设计文档创建正确的 `mtcg_card` 表与 `mtcg_product` 表（PostgreSQL DDL）。`mtcg_card` 表新增 `product_code` 字段关联产品。

### 设计意义

现有 `mtcg_card` 表字段（cost/attack/health）不符合《超英击战》规则。实际卡牌字段是 level（等级）、color（颜色）、attack_range（攻击距离 R）、power（战力）等。表结构是数据模型的物理实现，必须与规则文档对齐。

枚举字段用 VARCHAR 存名称 + CHECK 约束（设计原则：不存下标，存字符串名称），防止脏数据写入。

### 涉及文件

| 文件 | 操作 |
| --- | --- |
| `src/main/resources/sql/init.sql` | 重写 |

### 关键改动

```sql
CREATE TABLE IF NOT EXISTS mtcg_card (
    id              BIGSERIAL       PRIMARY KEY,
    card_code       VARCHAR(32)     NOT NULL UNIQUE,
    product_code    VARCHAR(16),                            -- 产品编号，如 BP01/SD01/PB01
    card_name       VARCHAR(128)    NOT NULL,
    card_type       VARCHAR(16)     NOT NULL,
    level           SMALLINT,
    color           VARCHAR(16),
    environment     VARCHAR(16),
    traits          VARCHAR(256),
    attack_range    SMALLINT,
    power           SMALLINT,
    rarity          VARCHAR(16)     NOT NULL,
    effect_text     TEXT,
    effect_json     TEXT,
    image_path      VARCHAR(256),
    create_time     TIMESTAMP       NOT NULL DEFAULT NOW(),
    update_time     TIMESTAMP       NOT NULL DEFAULT NOW(),
    CONSTRAINT ck_card_type CHECK (card_type IN ('CHARACTER', 'RUSH_POINT')),
    CONSTRAINT ck_color     CHECK (color IS NULL OR color IN ('RED','YELLOW','BLUE','GREEN','ORANGE','PURPLE')),
    CONSTRAINT ck_rarity    CHECK (rarity IN ('C','R','SR','GR','UR','MR','SEC','HR','LR','PR','ER','TR')),
    CONSTRAINT ck_level     CHECK (level IS NULL OR (level >= 1 AND level <= 6))
);

CREATE INDEX IF NOT EXISTS idx_card_type    ON mtcg_card (card_type);
CREATE INDEX IF NOT EXISTS idx_card_name    ON mtcg_card (card_name);
CREATE INDEX IF NOT EXISTS idx_card_color   ON mtcg_card (color);
CREATE INDEX IF NOT EXISTS idx_card_product ON mtcg_card (product_code);

-- 产品表（预组牌 / 补充包 / 推广包）
CREATE TABLE IF NOT EXISTS mtcg_product (
    id              BIGSERIAL       PRIMARY KEY,
    product_code    VARCHAR(16)     NOT NULL UNIQUE,
    product_name    VARCHAR(128)    NOT NULL,
    product_type    VARCHAR(16)     NOT NULL,
    release_date    DATE,
    description     TEXT,
    create_time     TIMESTAMP       NOT NULL DEFAULT NOW(),
    update_time     TIMESTAMP       NOT NULL DEFAULT NOW(),
    CONSTRAINT ck_product_type CHECK (product_type IN ('STRUCTURE_DECK', 'BOOSTER_PACK', 'PROMO_PACK'))
);
```

### 检验效果

- 启动应用，`init.sql` 自动执行（`spring.sql.init.mode: always`）
- 查看日志无 SQL 报错
- 用数据库工具连接 PostgreSQL，确认 `mtcg_card` 表已创建、字段正确、CHECK 约束存在
- 尝试插入一条非法数据（如 `color='BLACK'`），应被 CHECK 拒绝
- 确认 `mtcg_product` 表已创建，`mtcg_card` 表存在 `product_code` 列与 `idx_card_product` 索引

## 步骤 3：修正枚举体系

### 实现内容

1. 重构 `EnumCardType`：HERO/UNIT/EVENT/ITEM → CHARACTER/RUSH_POINT
2. 新建 `EnumColor`：6 种颜色
3. 新建 `EnumRarity`：12 种稀有度
4. 新建 `EnumProductType`：3 种产品类型（STRUCTURE_DECK / BOOSTER_PACK / PROMO_PACK）

### 设计意义

枚举是固定值的「单一真相来源」。用枚举而不是魔法字符串，代码可读性好、编译器能帮你检查拼写错误。

现有 `EnumCardType` 的值是通用 TCG 概念（英雄/随从/事件/道具），但《超英击战》只有两种卡：角色卡和冲击卡。必须与规则对齐。

枚举采用 `code`（存 DB）+ `desc`（中文显示）模式，与现有 `EnumCardType` 风格一致。

## 步骤 6：创建 DTO 与 VO

### 实现内容

创建卡牌相关的数据传输对象：

| 类 | 用途 | 包 |
| --- | --- | --- |
| `CardQueryDTO` | 查询入参（颜色、等级、名称、产品、分页） | `domain/dto` |
| `CardCreateDTO` | 新增/修改入参（卡牌全部字段） | `domain/dto` |
| `CardBatchImportDTO` | 批量导入入参（卡牌列表） | `domain/dto` |
| `CardVO` | 查询出参（卡牌全部字段 + 中文名展示） | `domain/vo` |
| `BatchImportResultVO` | 批量导入结果（成功数、失败数、失败详情） | `domain/vo` |
| `ProductQueryDTO` | 产品查询入参（产品类型、分页） | `domain/dto` |
| `ProductCreateDTO` | 产品新增/修改入参 | `domain/dto` |
| `ProductVO` | 产品查询出参 | `domain/vo` |

### 设计意义

**为什么 DTO 和 VO 要分开？**

- **DTO（Data Transfer Object）**：入参，带校验注解（`@NotBlank`、`@NotNull`），保护 API 安全
- **VO（View Object）**：出参，面向前端展示，可以附带额外信息（如颜色的中文标签）

如果用同一个类同时做入参和出参，会导致：
1. 入参字段被人篡改（如 id、createTime 不应该由前端传入）
2. 出参暴露不必要的信息（如 effect_json 内部字段）
3. 校验注解无法精确控制

这是阿里 Java 开发手册的标准分层规范。

## 步骤 7：实现 CardService

### 实现内容

创建 `CardService` 接口 + `CardServiceImpl` 实现类，实现以下方法：

| 方法 | 功能 | 核心逻辑 |
| --- | --- | --- |
| `getCardById(Long id)` | 查询详情 | 根据 ID 查询，不存在抛异常 |
| `listCards(CardQueryDTO query)` | 条件分页查询 | MyBatis-Flex QueryWrapper 构建条件 |
| `createCard(CardCreateDTO dto)` | 新增 | 校验编号唯一，DTO→DO 转换，插入 |
| `updateCard(Long id, CardCreateDTO dto)` | 修改 | 校验存在性，DTO→DO 转换，更新 |
| `deleteCard(Long id)` | 删除 | 校验存在性，删除 |
| `batchImport(CardBatchImportDTO dto)` | 批量导入 | 遍历列表，逐条插入，记录失败项 |

### 设计意义

Service 层是**业务编排中心**。它的职责是：

1. **参数校验**：检查编号是否重复、卡牌是否存在
2. **对象转换**：DTO → DO（入栈）、DO → VO（出栈）
3. **调用 DAO**：通过 Mapper 操作数据库
4. **异常抛出**：业务异常用 `BusinessException` 包装，带错误码

为什么不在 Controller 里直接调 Mapper？因为后续可能加缓存、加日志、加事务控制——这些都应该在 Service 层，Controller 只负责协议适配。

## 步骤 8：实现 CardController

### 实现内容

创建 `CardController`（6 个卡牌接口）与 `ProductController`（6 个产品接口）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/cards` | 分页查询卡牌列表 |
| GET | `/cards/{id}` | 查询卡牌详情 |
| POST | `/cards` | 新增卡牌 |
| PUT | `/cards/{id}` | 修改卡牌 |
| DELETE | `/cards/{id}` | 删除卡牌 |
| POST | `/cards/batch` | 批量导入 |
| GET | `/products` | 产品分页列表 |
| GET | `/products/{id}` | 查询产品详情 |
| POST | `/products` | 新增产品 |
| PUT | `/products/{id}` | 修改产品 |
| DELETE | `/products/{id}` | 删除产品 |
| GET | `/products/{productCode}/cards` | 按产品筛选卡牌 |

### 设计意义

Controller 层是**协议适配层**。它的职责很薄：

1. 接收 HTTP 请求，解析参数
2. 调用 Service
3. 把 Service 返回的结果包装成 `Result<T>` 返回

Controller **不应该**包含业务逻辑——没有 if-else 判断业务条件，没有数据库操作。这样做的 benefıc是：如果后续要加 WebSocket 或 gRPC 入口，Service 层可以直接复用。

路径统一 `/api/v1/...` 前缀（NFR9），由 `context-path: /api` + Controller 的 `/v1/cards` 组合实现。

| --- | --- |

## 步骤 9：集成验证

### 实现内容

端到端验证全链路：HTTP 请求 → Controller → Service → DAO → PostgreSQL → 返回。

### 设计意义

单独编译通过不等于功能正确。只有跑通完整链路，才能确认：
1. 数据库连接正常
2. SQL 语法正确
3. MyBatis-Flex 映射正确
4. 参数校验生效
5. 异常处理正常

### 验证用例

按以下顺序执行：

```
1. POST   /api/v1/cards          → 新增一张角色卡（如浩克）
2. POST   /api/v1/cards          → 新增一张冲击卡
3. GET    /api/v1/cards/{id}     → 查询刚创建的角色卡
4. GET    /api/v1/cards?color=RED&page=1&size=10 → 按颜色查询
5. PUT    /api/v1/cards/{id}     → 修改卡牌（改战力）
6. POST   /api/v1/cards/batch    → 批量导入 3 张卡
7. DELETE /api/v1/cards/{id}     → 删除卡牌
8. GET    /api/v1/cards/{id}     → 确认已删除（应返回 2001 错误）
```

### 检验效果

- 所有接口返回 `{"code": 0, "message": "操作成功", "data": ...}`
- 数据库中的数据与接口返回一致
- 传入非法参数（如 color=BLACK）时返回 400 错误
- 查询不存在的卡牌时返回 `{"code": 2001, "message": "卡牌不存在"}`
- 批量导入时部分失败不影响成功部分

## 步骤依赖关系

```
步骤1（切PostgreSQL）
  └→ 步骤2（重建表结构）
       └→ 步骤3（修正枚举）
            └→ 步骤4（修正CardDO）
                 ├→ 步骤5（补充ErrorCode）
                 └→ 步骤6（创建DTO/VO）
                      └→ 步骤7（实现Service）
                           └→ 步骤8（实现Controller）
                                └→ 步骤9（集成验证）
```

步骤 1-2 必须先做（数据库基础），步骤 3-6 可以一起做（代码基础），步骤 7-8 有依赖关系（Service 先于 Controller），步骤 9 是最终验证。
