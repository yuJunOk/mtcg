# AI 辅助项目启动指南

> 本文档梳理了借助 AI 从零启动一个软件项目的完整流程，既可供人类复盘参考，也可作为 AI 执行的规范指引。

---

## 一、流程总览

```
规则/需求梳理 -> 文档体系搭建 -> 软件设计 -> AI编码规范 -> 工程结构 -> 仓库初始化 -> 迭代开发
```

共 **7 个阶段**，每个阶段都需要人机协作，逐步收敛。

---

## 二、阶段详解

### 阶段 1：领域知识梳理（规则/需求输入）

**目标**：把业务领域的原始资料整理成结构化文档。

**人做什么**：
- 提供原始资料（规则书、需求描述、参考链接、图片等）
- 判断 AI 整理的质量，给出修正意见

**AI 做什么**：
- 阅读全部资料，评估文档拆解质量
- 检查逻辑一致性、术语统一性
- 建议文档编号和命名规范
- 发现资料中的图样问题、表达歧义

**关键产出**：
```
docs/
├── 01-快速入门规则.md
├── 02-综合规则书-vX.X.md
├── 03-术语表与关键词速查.md
├── 04-区域模型与回合流程.md
└── README.md（文档索引）
```

**经验总结**：
- 原始资料中的图片要单独归档（`快速入门图片/`、`规则书图片/`）
- 术语表和规则书要交叉引用，确保关键词定义一致
- 规则文档编号要稳定，后续设计文档通过编号引用规则条款

---

### 阶段 2：文档体系搭建

**目标**：设计清晰的文档目录结构，为后续所有文档建立"家"。

**核心决策：双层 docs 结构**

```
项目根目录/
├── docs/                    ← 全局共享文档（所有模块共用）
│   ├── 规则文档/            ← 游戏规则、业务规则
│   ├── 设计文档/            ← 需求分析、概要设计、详细设计
│   ├── 编码规范/            ← 通用编码规范
│   └── README.md            ← 全局文档索引
├── mtcg-server/             ← 后端模块
│   ├── docs/                ← 后端专属技术文档
│   └── AGENTS.md            ← AI 规则入口
├── mtcg-client/             ← 前端 Monorepo
│   ├── packages/
│   │   ├── common/          ← 共享包（PixiJS、Pinia、API）
│   │   ├── game-pc/         ← PC 端（Electron）
│   │   └── game-mobile/     ← 移动端（Capacitor）
│   └── docs/                ← 前端专属技术文档
└── README.md
```

**为什么双层 docs**：
- 全局 `docs/` 放共享文档：规则、需求、设计、编码规范
- 模块 `docs/` 放专属文档：技术研究、Bug 研究、模块方案
- 避免一个 docs 目录膨胀到无法管理

**经验总结**：
- 前后端 docs 分开，因为研究关注点不同
- 文档目录提前规划好分类，不要等多了再整理
- 每层 docs 都要有 README.md 作为索引

### 阶段 3：软件设计（规范流程）

**目标**：按标准软件工程流程，逐步产出设计文档。

**关键原则：一步步来，不要一顿输出**

#### 3.1 需求分析

**流程**：
1. AI 生成需求分析初稿
2. 用户逐节审查，提出修改
3. AI 修订后再确认
4. 双方对需求达成一致后，再进入下一阶段

**需求分析文档结构**：
```markdown
# 需求分析
## 1. 项目背景与目标
## 2. 用户角色（系统管理员/卡牌管理员/玩家/AI玩家...）
## 3. 功能需求（FR1-FRn，含优先级）
## 4. 非功能需求（性能/安全/可用性...）
## 5. 技术选型决策（含理由）
## 6. 决策记录表（每个关键决策记录选择和理由）
```

**经验总结**：
- 用户角色要考虑全：别忘了系统管理员
- 功能需求要标优先级（高/中/低/未来）
- 技术选型要有理由，不能只写结论（如为什么选 PostgreSQL 而非 SQLite）
- 决策记录表非常重要，以后复盘能看到"当时为什么这么选"

#### 3.2 概要设计

**产出**：
- 包结构设计
- ER 图（数据库表关系）
- 核心类设计
- API 清单

#### 3.3 详细设计（按迭代）

**按迭代拆分，每个迭代一个文档**：

```
设计文档/
├── 01-需求分析.md
├── 02-概要设计.md
├── 03-详细设计-迭代一-卡牌数据落地.md
├── 04-详细设计-迭代二-用户系统与权限管理.md
├── ...
├── 12-详细设计-迭代十-系统管理.md
└── 13-实现步骤-迭代一-卡牌数据落地.md
```

**迭代拆分原则**：
- 先数据后逻辑（卡牌数据 -> 用户系统 -> 卡组构筑 -> 引擎 -> 对战 -> AI -> 排位 -> 管理）
- 每个迭代可独立交付、可测试
- 实现步骤文档单独产出，指导编码

---

### 阶段 4：AI 编码规范

**目标**：建立 AI 代码生成的"宪法"，确保每次 AI 编码都遵循规范。

#### 4.1 编码规范文档

**存放位置**：`docs/编码规范/AI编码规范.md`

**内容要点**：
- 分层架构规范（controller -> service -> manager -> dao）
- 命名规范（类名、方法名、变量名、表名前缀）
- 枚举规范（如用户偏好 enum 前缀）
- 注释规范
- 包结构规范

#### 4.2 AGENTS.md（AI 规则入口）

**关键**：在每个工程模块根目录创建 `AGENTS.md`，作为 AI 每次编码前必须读取的入口文件。

```markdown
# 项目 AI 规则入口

> **每次编码前必须读取以下文件：**
> 1. [docs/AI编码规范.md](./docs/AI编码规范.md)
> 2. 对应迭代的详细设计文档

## 设计文档索引
| 文档 | 说明 |
| --- | --- |
| ... | ... |

## 规则文档索引
| 文档 | 说明 |
| --- | --- |
| ... | ... |

## 当前迭代
**迭代一：xxx** - 参照 [实现步骤](xxx)
```

**经验总结**：
- AGENTS.md 是确保 AI 编码一致性的关键
- 编码规范要放项目内部，不要放外部目录
- 索引表让 AI 快速定位需要读取的文档
- "当前迭代"字段明确 AI 本次编码的上下文范围

### 阶段 5：工程结构规划

**目标**：确定工程命名、目录结构、技术栈。

#### 5.1 命名规范

**原则**：统一前缀，支持未来扩展

```
mtcg/                        ← 仓库根目录（项目代号）
├── mtcg-server/             ← 后端服务
├── mtcg-client/             ← 前端 Monorepo（PC + 移动端游戏客户端）
│   ├── packages/common/     ← 共享包
│   ├── packages/game-pc/    ← PC 端
│   └── packages/game-mobile/← 移动端
├── assets/                  ← 静态资源
├── scripts/                 ← 工具脚本
└── docs/                    ← 全局文档
```

**为什么用前缀**：
- 未来拆分为多模块时，命名天然支持
- 不同终端（PC/移动端）在 Monorepo 内以 packages 区分
- GitHub 仓库搜索友好

#### 5.2 技术栈确定

| 层 | 技术选型 | 决策理由 |
| --- | --- | --- |
| 后端框架 | Spring Boot 3.5 + Java 17 | 成熟稳定，生态丰富 |
| ORM | MyBatis-Flex | 类型安全，代码简洁 |
| 数据库 | PostgreSQL 16 | 支持在线对战，并发性能好 |
| AI 框架 | Spring AI | 后端集成 AI 能力 |
| 前端框架 | Vue 3 + Vite | 管理后台首选 |

#### 5.3 前端工程结构（Monorepo）

```
mtcg-client/
├── package.json                 ← npm workspaces 根配置
├── docs/                        ← 前端专属文档
├── packages/
│   ├── common/                  ← 共享包（所有端共用）
│   │   └── src/
│   │       ├── types/           ← TS 类型定义（对应后端 GameState）
│   │       ├── api/             ← Axios REST API 封装
│   │       ├── stores/          ← Pinia 状态管理
│   │       └── engine/          ← PixiJS 游戏画布（共用）
│   ├── admin-web/               ← 管理后台（Vue 3 + Element Plus）
│   │   ├── src/
│   │   │   ├── layouts/         ← 侧边栏 + 顶部标题栏布局
│   │   │   ├── views/dashboard/ ← 仪表盘
│   │   │   ├── views/card/      ← 卡牌管理 CRUD 页面
│   │   │   └── views/product/   ← 产品管理 CRUD 页面
│   │   └── package.json
│   ├── game-pc/                 ← PC 端（横屏 + Electron 打包）
│   │   ├── electron/main.js     ← Electron 主进程
│   │   └── src/views/           ← PC 专属视图
│   └── game-mobile/             ← 移动端（竖屏 + Capacitor 打包）
│       └── src/views/           ← 移动端专属视图
```

**核心设计**：
- `packages/common`：PixiJS 游戏引擎、Pinia 状态管理、API 封装 —— 所有端共用，view 分开
- `packages/admin-web`：管理后台，使用 Element Plus 组件库，复用 common 的 API 和类型
- `packages/game-pc`：横屏布局，Electron 打包为 Windows exe
- `packages/game-mobile`：竖屏布局，Capacitor 打包为 Android apk / iOS ipa
- `pixi.js` 作为 `peerDependency` 下放到 `game-pc`/`game-mobile`，`admin-web` 不依赖重型渲染库

**历史调整**：
- 曾考虑独立目录 `mtcg-admin-web`，现已废弃，合并到 `mtcg-client/packages/admin-web`

**经验总结**：
- 管理后台应优先开发（数据录入是后续开发的基础）
- 前端 docs 和后端 docs 分开，关注点不同
- 命名用 `mtcg-` 前缀，不用 `hero-rush-tcg` 这种业务名称

### 阶段 6：仓库初始化

#### 6.1 GitHub 仓库创建

**步骤**：
1. 在 GitHub 线上新建仓库
2. 填写信息：
   - 仓库名：`mtcg`（简洁明了）
   - 描述：一句话说明项目
   - 可见性：Private（开发阶段）
   - 初始化：不勾选 README/gitignore（本地已有）
3. 本地关联远程仓库

#### 6.2 README 编写

**好的 README 要素**：
- Banner 图片（宽度适中，280px 左右）
- 项目名称 + 一句话描述
- 技术栈徽章（ shields.io ）
- 项目结构树
- 模块概览表
- 快速启动指南
- 文档导航
- 官方资源链接
- 版权声明

**经验总结**：
- Banner 图片不要太占空间，用户要一眼看到内容
- 项目命名不要混用（官方内容用原名，自有内容用 mtcg）
- Logo 等图片资源放 `assets/` 目录，不要只依赖外链

## 三、人机协作原则

### 3.1 分工模式

| 环节 | 人类职责 | AI 职责 |
| --- | --- | --- |
| 需求 | 提供业务知识、做决策 | 整理、分析、提问引导 |
| 设计 | 审查、确认、纠偏 | 产出方案、提出选项 |
| 编码 | 审查、验收 | 编码、测试、文档 |
| 规范 | 制定原则、拍板 | 落地执行、检查一致性 |

### 3.2 沟通原则

1. **不要一顿输出**：AI 每次输出一个阶段，用户确认后再继续
2. **给选项不给答案**：技术选型时，AI 给出选项和理由，用户拍板
3. **问比答重要**：AI 主动提问引导用户思考（如"需要系统管理员吗？"）
4. **评分机制**：每个阶段完成后，AI 自评 + 用户评分，持续改进
5. **决策要留痕**：关键技术选型记录在决策记录表中

### 3.3 常见坑与对策

| 坑 | 对策 |
| --- | --- |
| AI 一次性输出太多 | 明确要求"一步步来" |
| 文档路径引用失效 | 调整目录后全局检查引用 |
| 编码规范形同虚设 | 创建 AGENTS.md 强制 AI 读取 |
| 命名混乱（业务名/技术名混用） | 明确：官方内容用原名，自有内容用项目代号 |
| 前端被忽视 | 管理后台优先开发，为数据录入打基础 |
| 技术选型未考虑未来 | 决策时问"未来要在线对战，还合适吗？" |
| **模块命名不一致** | 命名确定后写入编码规范，禁止 AI 擅自更改（见下方专题） |
| **README 内容归属混乱** | 全局内容（游戏概要/功能模块/开发路线）归根 README，模块专属内容归模块 README |
| **图片素材不是有效文件** | 下载后用 `Format-Hex` 验证文件头（PNG = `89 50 4E 47`），不能只写入 URL 文本 |
| **LICENSE 与声明不符** | 声明"非商业用途"时选 CC BY-NC 4.0，不用 MIT |
| **PowerShell 不支持 heredoc** | `git commit -m` 用多个 `-m` 参数替代，不用 `$(cat <<'EOF')` |
| **git push SSL 握手失败** | 网络临时问题，代码已提交到本地，网络恢复后重新 push |
| **PowerShell 全局替换损坏文件** | 中文文件名/内容用 `-replace` 时注意编码，优先用 SearchReplace 工具 |
| **空目录不被 git 追踪** | 新建目录时放 `.gitkeep` 文件，否则 `git checkout` 后目录消失 |

### 3.4 模块命名一致性专题

**问题**：AI 在不同轮次对话中，对同一模块使用了不同命名（如 `mtcg-admin-web` / `mtcg-client-admin` / `admin-web`），导致文档、代码、目录名不一致。

**根因**：AI 没有将命名规范固化到文档中，每次对话靠记忆，容易混淆。

**对策**：
1. 项目初期确定命名规范（如 `mtcg-` 前缀 + 面向用户 + 终端类型），写入编码规范
2. 编码规范中明确列出正确名称和禁止变体
3. 每次新建目录/文件前，先查编码规范
4. 全局搜索确认无残留的旧名称

**命名规则**：
```
mtcg-                  ← 项目前缀
├── server             ← 后端不带终端后缀
└── client             ← 前端 Monorepo
    └── packages/
        ├── common     ← 共享包
        ├── admin-web  ← 管理后台（Vue 3 + Element Plus）
        ├── game-pc    ← PC 端游戏（Electron）
        └── game-mobile← 移动端游戏（Capacitor）
```

**已废弃名称**：
- `mtcg-admin-web` —— 管理后台不再作为独立目录，已合并到 `mtcg-client/packages/admin-web`
- `mtcg-client-web` —— 玩家端统一在 `mtcg-client` Monorepo 内，不再使用此命名

### 3.5 前后端协同规范专题

**枚举对齐**：前端枚举文件必须与后端 `common/enums` 下的枚举类**逐一对应**，每个后端枚举类对应一个独立前端文件，不合并到同一文件。增删改查时能快速定位。

**Monorepo 共享**：`packages/common` 是 PC 和移动端的共享层，包含 PixiJS 引擎、Pinia 状态、API 封装、TS 类型定义。两端只需各自实现 view 层，游戏逻辑和状态管理不重复维护。

**OpenAPI 生成请求方法**：后端 SpringDoc 提供 `/v3/api-docs`，前端用 `openapi-typescript-codegen` 自动生成 TS 请求方法，保证接口契约一致。后端接口变更后重新生成，避免手写 URL 和参数错误。生成的代码禁止手动修改。

**实现步骤状态跟踪**：实现步骤文档中每个步骤标注状态（🔲 未开始 / 🚧 进行中 / ✅ 已完成）。调整步骤时不得覆盖已完成步骤的状态，只增改未完成部分。

## 五、优化建议（未来改进方向）

1. **需求分析阶段引入用户故事**：用 User Story 格式描述需求，更贴近用户视角
2. **设计文档增加时序图**：复杂交互流程用时序图描述，减少歧义
3. **编码规范增加示例代码**：每种规范配一个正例和反例
4. **迭代开发增加验收标准**：每个迭代明确 Done 的定义
5. **建立术语词典**：业务术语和技术术语统一管理
6. **引入 API 契约**：前后端用 OpenAPI/Swagger 定义接口契约
7. **自动化文档检查**：CI 中检查文档路径引用是否有效
8. **复盘模板**：每个迭代结束后填写的复盘模板

---

## 六、适用场景

本流程适用于：
- **从零启动的软件项目**（有明确业务领域）
- **需要 AI 深度参与的项目**（不仅是写代码，还包括设计、文档）
- **中大型项目**（需要多迭代、多模块协作）
- **团队中有非技术成员**（需要清晰的文档和沟通）

不适用于：
- 一次性脚本/工具
- 纯研究性项目
- 已有成熟框架的简单二次开发

---

> **最后的话**：AI 是放大器，好的流程让 AI 放大效率，坏的流程让 AI 放大混乱。流程本身需要持续迭代优化。
